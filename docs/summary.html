Developer summary

gitdash

PC内に散在するGitリポジトリを登録なしで見つけ、状態・履歴・ブランチを読み取り専用で一覧するローカルダッシュボード。Docker Composeで常駐し、利用者は http://localhost:4412 から確認する。

対象実装: backend/app/main.py・scanner.py・watcher.py・gitinfo.py・detail.py・graph.py、frontend/app/graph-view.tsx・repo-detail.tsx・page.tsx、docker-compose.yml

目的と裏テーマ

表の目的

どのリポジトリに手をつけるべきかを一目で分かるようにする。未コミット、未push、上流との差分、分岐、放置されたブランチを、リポジトリごとに確認できる。

裏テーマ（設計の背骨）

使っているうちにGitコマンドを覚えられること。状態表示は独自記法ではなく git status -sb の語彙を保ち、各ビューには人間が同じ情報を見るためのコマンドを出す。状態から「次に打つコマンド」を1つだけ提示する。

pull / pushボタンは置かない。操作はターミナルで行う必要を残すことで、git pull --ff-only や git push を状況と結びつけて覚えるための学習装置にしている。

全体構成

ブラウザ / Next.jspage.tsx がプロジェクト階層、検索、フィルタ、remote repository単位のグループ化を担当。詳細は repo-detail.tsx、グラフの各行は graph-view.tsx。
Next API proxyapp/api/[...path]/route.ts が /api/* を実行時の BACKEND_ORIGIN へ転送。SSEのbodyはそのまま返す。
FastAPI backendSTATE（ホストパスをキー）とキャッシュを持ち、探索・git取得・グラフ・詳細・ブランチAPIを提供。backendのポートは外部公開しない。
Git / filesystemホストと同じ絶対パスへ走査ルートをmountし、linked worktreeの .git ポインタを解決する。実体gitdirと共有refs/logsをinotifyで監視する。

Composeではfrontendだけが 4412:3000 を公開し、backendは expose: 8000 のみ。backendはホストのuid/gidで動作し、fetchのためマウントはrw。アプリはfetch以外に明示的な変更操作を行わないが、git status が .git/index を書き戻すことはある。ローカル処理用poolとfetch用fetch_poolは分離されている。

画面からbackendまで

  • page.tsx は EventSource("/api/stream") でスナップショットと差分イベントを受け、画面内の行を IntersectionObserver で集めて POST /api/refresh に送る。フォーカス復帰時にも可視行を再取得する。
  • リポジトリを開くと repo-detail.tsx がグラフとブランチを取得する。グラフ行を選択すると150msのデバウンス後にコミット詳細を取得する。--all とマージ済みブランチ表示は画面側の切り替え。
  • APIハンドラの _known_repo() は、受け取ったpathが現在の STATE に存在する場合だけ許可し、コンテナ内パスへ変換する。グラフ・詳細・ブランチのGit実行はすべてリポジトリ単位の _repo_lock() を通る。

SSE（Server-Sent Events）

GET /api/stream の接続直後に snapshot（現在のリポジトリ配列）を送り、その後はbackendのBusがイベントを配信する。イベントループに紐づいた購読Queueを使い、20秒イベントがなければkeepaliveコメントを送る。

イベントdata発生箇所
snapshotリポジトリオブジェクトの配列接続時。activity降順
repo更新済みリポジトリオブジェクト探索でstubを発見、またはGit状態の取得完了
scan{active: boolean, found: number}探索開始・終了
done{count: number}全体取得完了
removed{path: string}探索で消えたリポジトリ
fetch{active: boolean, total: number}背景fetchの開始・終了

探索とinotify

起動時は新しいworktree契約を満たすキャッシュを先に読み、背景で探索を行う。探索で本体を見つけると、共通リポジトリのロック内で git worktree list --porcelain を一度実行し、走査対象外の .cursor/worktrees や .claude/worktrees もSTATEへ補完する。活動時刻は実体gitdirの logs/HEAD を使う。

Watcherは通常リポジトリのgitdir、linked worktree固有のgitdir、共有refs/logsを監視する。イベント名が .lock で終わるものは破棄し、残りは取得完了後3秒の抑止、1秒の共通リポジトリ単位デバウンス、common_dir 単位の排他を経て再取得する。作業ツリーのファイル編集自体は .git を変えないため、frontendのフォーカス復帰時取得で補う。

リポジトリ状態のworktree契約

グラフのレーンと描画

graph.py は git log --date-order --decorate=full --parents 相当の親情報から、行をまたいで生きる枝をレーン番号に割り当てる。frontendはその番号を受け取って曲線を描く。

フィールドこの行での意味frontendの描画
laneこのコミットのノードが置かれるレーン。ノード中心のx座標。レーン幅14px、左余白8px。
in_lanes上から降りてきて、このコミットに入る線。マージで複数になることがある。各レーン上端からノード中心までを直線または曲線で結ぶ。
throughこのコミットには関係せず、同じ行を通過する別枝。そのレーンの上端から下端まで直線を引く。
out_lanesこのコミットから親へ出る線。配列順が親の順序。ノード中心から行下端へ直線または曲線で結ぶ。

なぜ「1行 = 1枚のSVG」か

1000コミットを1枚の巨大SVGにまとめると、DOM・再描画・クリック処理が重くなり、仮想スクロールとも両立しない。そこで各コミット行が自分の行を通る線分とノードだけを、高さ30pxの小さなSVGとして持つ。行ごとの再描画と通常のスクロールを保ちつつ、レーンの縦位置は全行で固定幅にする。

W = 14px, H = 30px
node = (min(lane, 7) * W + 8, H / 2), radius = 4
through[i]  : (min(i, 7)*W+8, 0) → (min(i, 7)*W+8, H)
in_lanes[i] : (min(i, 7)*W+8, 0) → node
out_lanes[i]: node → (min(i, 7)*W+8, H)
SVG width   : min(max_lane + 1, 8) * W + 16

lane の値はAPIに保持するが、frontendの座標は8レーン分に収める。レーン番号8以上の枝は描画上、最後のレーン位置に重なる。

未コミット変更があるときは、repo.branch_line（git status -sb相当）とXYコード集計を持つ破線丸の仮想ノードを最上部に追加する。レーンは head_lane で、現在の作業がどのコミット系列の上に乗っているかを示す。

refバッジは head を強調、remote を淡く、tag を別色で表示する。既定は all=false で現在ブランチとupstreamを見せ、トグルで --all に切り替える。

踏んではいけない罠

1. inotify自己励起ループ

git status は作業ツリーのstat変化に応じて .git/index を書き戻すことがある。これをinotifyが拾って再取得し、再取得中のGitがまたindexを書き、無限に自己励起する。検証時にはアイドル10秒で1968イベント、同時実行時には index.lock の競合が発生した。

次の3層を外さないこと: (1) Watcherで .lock イベントを破棄、(2)取得完了から SUPPRESS_SEC = 3.0 秒は対象repoのイベントを無視、(3) _repo_lock() で同一repoのGit実行を排他。さらに DEBOUNCE_SEC = 1.0 秒で複数イベントをまとめる。新しいGit呼び出しは直接 gitinfo._run() せず、必ずrepo lockを通す。

2. Next.js rewritesの実行時固定だと思い込む

next.config.mjs の rewrites は next build 時点で評価される。Compose起動時に BACKEND_ORIGIN を差し替えても、ビルド時に決まった転送先は変わらない。

現在は frontend/app/api/[...path]/route.ts のNode.jsルートハンドラで、リクエスト時に process.env.BACKEND_ORIGIN を読む。dynamic = "force-dynamic" とし、SSEはupstreamのbodyを触らずストリームとして返している。proxyをrewritesへ戻さないこと。

変更時のチェックポイント

  • 新しいrepo APIでは、最初にSTATE存在確認を行い、ホストパスをそのままGitに渡さない。
  • Gitを呼ぶ処理はrepo単位の排他を通す。fetchはローカル取得を詰まらせないため別poolを使う。
  • グラフ行のフィールド名（特に lane / in_lanes / through / out_lanes）と、APIの remotes キーを変更する場合はbackendとfrontendを同時に確認する。
  • 表示用コマンドは内部のporcelainやformat文字列そのものではなく、利用者がターミナルで打つ等価なコマンドにする。
  • 作業ツリー編集はinotifyの責務外。画面復帰時の可視行refreshを外すと、保存直後の状態が古いままになる。
