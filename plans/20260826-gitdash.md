# gitdash 実装計画

PC内の Git リポジトリを登録なしで一覧する読み取り専用ダッシュボード。
Linux / Docker Compose 前提。

## 要件

- リポジトリの登録作業をしない。ディスクを走査して `.git` を自動発見する
- 表示は git コマンドレベルの一般的な情報のみ
- 独自記号を作らない。`git status -sb` の表記をそのまま使う
- pull 可能かどうかを判定する（fetch して ahead/behind を取る）
- 大量のリポジトリでも体感を遅くしない
- Docker Compose、`restart: always`、公開ポートはフロントの 4412 のみ

## 裏テーマ

使っているうちに git コマンドを覚えられること。
そのために2つ入れる。

1. 各ビューに、そのビューと等価な人間向けコマンドを表示する
   （実際に叩いている `--porcelain=v2` ではなく `git status -sb` を出す）
2. リポジトリの状態から「次に打つコマンド」を1つだけ提示し、コピーできるようにする

pull / push ボタンは作らない。実行するにはターミナルへ行く必要がある状態を維持する。

## 構成

```
docker compose
├── frontend (Next.js)  ports 4412:3000   ← 唯一の公開ポート
└── backend  (FastAPI)  expose 8000       ← 公開しない
```

backend に直接ブラウザからは到達できないため、frontend の `rewrites` で
`/api/*` を `http://backend:8000/api/*` へプロキシする。SSE もここを通す。

ホストの走査対象を backend に bind mount する。
コンテナ内パスは `/scan` 固定、表示はホストパスへ変換して返す。

## 速度設計

律速は探索ではなく `git status`。Linux ではプロセス生成が安いので、
コマンド数を削るより並列度と順序で解く。

| 時刻 | 画面 |
|---|---|
| 〜10ms | キャッシュから全行が並ぶ（前回値、淡色表示） |
| 〜1s | 画面内の行が最新値に置き換わる |
| 〜数秒 | 残りが埋まる。活動が新しい順 |
| 背景 | 再探索で新規追加、fetch で ahead/behind 更新 |

打ち手:

1. **パス一覧を永続化** — 起動時は探索せず、キャッシュのパスを `isdir` 検証して即表示
2. **活動順ソート** — `.git/logs/refs/HEAD` の mtime。`os.stat` 1回で取れるので
   git を1度も起動する前に並べ替えられる
3. **可視優先** — フロントの `IntersectionObserver` が画面内のパスを
   `POST /api/refresh` に送り、そこから先に処理する
4. **SSE で逐次配信** — 探索で見つかった時点でパスだけ流し、状態は後から埋める
5. **inotify** — `.git` を watch し、commit / checkout / pull / stash を即座に反映。
   以降は全体スキャンをしない

inotify の限界: 作業ツリーのファイル編集では `.git` は変化しないため
`M` / `??` は拾えない。フォーカス復帰時と手動更新時に取り直す。

## 除外

- `SKIP` に Linux 向けの重いディレクトリ（`go/pkg`, `.cargo`, `.npm` など）
- `/proc` `/sys` `/dev`
- ネットワークマウント（`/proc/mounts` を読み fstype で判定）

## fetch のハング対策

Linux では `GIT_TERMINAL_PROMPT=0` だけでは足りない。SSH 鍵が
ssh-agent に載っていないとパスフレーズ待ちで固まる。

```
GIT_TERMINAL_PROMPT=0
GIT_SSH_COMMAND=ssh -oBatchMode=yes -oConnectTimeout=5
GIT_ASKPASS=true
SSH_ASKPASS=true
```

fetch はローカル処理とは別プール（既定4並列）。`last_fetched_at` を持ち
既定5分以内はスキップ。

## 次のコマンドの対応表

上から順に評価し、最初に一致したものを出す。
作業ツリーが汚れているときは pull を勧めない（失敗するため）。

| 条件 | 提示 |
|---|---|
| コンフリクトあり | `git status` |
| 未ステージあり | `git add -p` |
| 未追跡のみ | `git add -A` |
| ステージ済みのみ | `git commit` |
| upstream なし | `git push -u origin <branch>` |
| ahead > 0 かつ behind > 0 | `git pull --rebase` |
| behind > 0 | `git pull --ff-only` |
| ahead > 0 | `git push` |
| それ以外 | なし |

## 判断の記録

- **マウントは rw** — fetch が `.git` への書き込みを要するため。ro にすると
  pull 可能かどうかの判定ができない。アプリ側は fetch 以外書き込まない
- **backend は host uid で動かす** — root で動かすと git の `safe.directory`
  に引っかかり、生成物の所有者も汚れる
- **stash 数とリモート URL も git に聞く** — `.git` を直接読むほうが速いが、
  Linux ではプロセス生成が安く、差は誤差。正確さを取る

## 実装中に見つかった問題と対処

### 1. inotify の無限ループ（重大）

`git status` は作業ツリーの stat 情報が変わると `.git/index` を書き戻す。
これを inotify が拾い、再取得を起こし、また index が書かれる、という自己励起。
検証環境ではアイドル10秒で 1968 イベント。同時実行で `index.lock` の
奪い合いも発生し、リポジトリが操作不能になった。

3層で塞いだ。

- `.lock` で終わるファイルのイベントを watcher が捨てる
- 取得完了時刻から 3 秒間はそのリポジトリのイベントを無視する（自己発火の抑止）
- リポジトリ単位の排他ロックで、同じリポジトリに対する git の並行実行を防ぐ

加えて、1 操作で複数イベントが出るため 1 秒のデバウンスでまとめる。
対処後はアイドル 0 件、commit 1 回につき 1 件になった。

### 2. rewrites の行き先がビルド時に固定される

`next.config.mjs` の `rewrites` は `next build` の時点で評価されるため、
compose の `BACKEND_ORIGIN` を実行時に渡しても効かない。環境変数が
何もしない飾りになる罠だった。

`app/api/[...path]/route.ts` のルートハンドラに置き換え、リクエストごとに
`process.env.BACKEND_ORIGIN` を読むようにした。SSE は `upstream.body` を
そのまま返して素通しし、backend 停止時は 502 と JSON を返す。

## 検証済みの項目

- 除外リストが効く（`node_modules` 配下を拾わない）
- 3 階層下のリポジトリを発見できる
- porcelain v2 の XY コードが `git status -sb` の表記に戻る
- `ahead 1` の再現とブランチ行の組み立て
- リモート未設定時に push を提案しない
- SSE の snapshot / repo / scan / done イベント
- 可視優先の `POST /api/refresh`
- inotify が commit を 1 件だけ拾う
- フロントの本番ビルドとプロキシ経由の全経路
